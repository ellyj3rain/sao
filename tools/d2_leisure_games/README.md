acquired object instance, installed source revision, and maintained purpose.
Source effects occur through the native timed action. Canonical detached outcomes
retain real attempted progress; an interrupted session does not become a win.

## API

`offers`, `intentOffers`, `begin`, `work`, `advance`, `outcome`, `interrupt`, and
`reset` use the standard personal hobby owner signatures. `begin` calls
`ProceduralPlanning.admitHobbyWork` before queueing a source action. Every native
effect rechecks the maintained typed admission; canonical terminal storage
precedes `consumeHobbyOutcome`.

For computer play, `context(id, body)` exposes the current source renderer's
`commands` and `labels`, with actor/work/source/revision/frame/county-time
bindings and a logical 450 by 253 viewport. `controlPresentation` returns the
same bindings and original source labels. It omits the drawing command stream.
Neither query reveals an engine grid, seed, future event, hidden mine, secret
code, or opponent backend state. The source renderer determines which facts are
presently shown.

`inputOffers(id, body)` supplies release plus source-valid single/pair controls;
`submitInput(id, body, exactOffer)` reconstructs current offers, accepts once
per frame, and retains the selected held keys until the next selection. The
decision owner supplies the person's policy. This provider has no scripted
solution or automatic win selection.

Computer and ping-pong source backends persist at admission/start/update and
on interruption, bounded to 32 source/station/machine entries. Native Kahlua
serialization is exercised. Restoring a backend preserves its original random
state and does not reset or reroll its board or generated match. Runtime absence
retires saved work and releases only its exact acquired owned leases; it cannot
restore an old native callback. Original arcade interruption consumes its paid
session, retains source consequences, and requires a new source payment for a
new session.

## Source adaptations and verification boundary

`source_profile.py` creates lexical actor-specific classes and preserves original
source functions. Private input/drawing/UI-sound receivers prevent operator
keyboard, player panel, camera, and singleton ownership changes. Source control
labels remain original; `fakeRival` retains its precise source qualification.
The ping-ball camera/slot presentation is replaced with original world/arc math.
Source debug animation-name speech is represented by the actual body animation.
Arcade halo presentation is actor-owned, while substantive stats, sound, screen,
payment, and result operations remain the source's operations. Computer and
arcade wall-clock checks use the county clock. The separately defined computer
`updateGameMoodEffects` method has no installed call site and is not invoked;
the installed live OnPlayerUpdate mood callback is preserved.

The computer requires an actually powered, already initialized, powered-on,
password-free, intact machine with installed OS and game software. Native
initialization, credentials, power controls, and software installation retain
their original ownership. Revision receipts pin audited original bytes;
`revisionAuthority` states that an authenticated loaded-byte seal is unavailable.

Run `C:/Python314/python.exe tools/d2_leisure_games_test.py --output <new path>`.
The test executes unmodified installed computer/arcade sources beside the
isolated owner in installed Kahlua and compares mechanics, RNG, presented
frames, native mood receivers, coin custody, source overlays, and results.
Mutation controls must fail at the relevant asserted contract. Native body,
power, visibility, queue, texture/audio and inventory receivers are controlled.
This is not a loaded NPC, actual GPU-rendered screen, human partner agreement,
learned mastery, prevalence, or whole-D2 closure receipt.

## Adjacent native inventory trace

Native `VideoGame`, `CardDeck`, chess pieces, checkerboard and dice items exist
in `media/scripts/generated/items/normal.txt`. Searches across installed client,
shared and workshop Lua found no actual portable-video-game or board-game rules.
Generated `recipes_cardsAndDice.txt` does define `DrawRandomCard` and
`RollOneDice` with Java `RecipeCodeOnCreate` callbacks. These are real card/dice
operations, rather than full board-game rules.

The installed Java callbacks call `HaloTextHelper.addGoodText(IsoPlayer, ...)`;
that presentation indexes global queued player lines by `IsoPlayer.getIndex()`.
An external NPC therefore needs an isolated source-grounded native result
adapter before the callbacks can safely join this owner. That trace is a
remaining native seam, not evidence that card/dice mechanics are absent.
